# 性能与容量

> [← 首页](Home-zh) · 上一篇：[访问控制](Access-Control-zh)

完整推导见项目内部容量分析文档，本页是结论速查。

> **基线：0.4.0（sherpa-onnx 引擎；vosk 已移除）。** 文件体积取自随包模型的实测；
> 内存/CPU 数字为工程估算（模型权重 + ONNX Runtime 开销 + 实现设计文档的验收门槛），
> 实测回归落地前以此为准。

## 瓶颈画像

| 资源 | 量级 | 说明 |
|---|---|---|
| 网络 | ~3 KB/s / 说话玩家（Opus 24 kbps） | 走原版连接，**永远不是瓶颈**；`maxFramesPerSecond=15` 时上限 9 KB/s |
| 内存（流式引擎） | **~250–400 MB / 说话玩家**（估算）——当前无共享层 | `sherpa-zh-en` 每会话加载 int8 权重：encoder 182 + decoder 13 + joiner 3 MB ≈ 199 MB，再加 ONNX Runtime 开销；2 解码线程。模型目录同附带的 fp32 变体运行时不会加载 |
| 内存（IPA） | 400–600 MB，**全服仅一次** | `ipa-phonemes`：230 MB q4 权重挂在进程级共享 ONNX 会话上；玩家会话本身很薄 |
| 内存（SenseVoice，规划中） | 目标 ≤ 400 MB 共享（跨源估算 365–650 MB） | 离线整句引擎（zh/en/ja/ko）：共享单例 + 串行解码；模型暂未随包 |
| CPU（流式） | 每流 RTF ≤ 0.15 @ 2 线程（验收门槛） | 即说话期间每玩家约占 0.15–0.3 核 |
| CPU（IPA） | 每句话 0.5–2 秒推理，共享解码池固定 `min(4, 核数-1)` 线程 | **结构性瓶颈**：并发说话多时排队 |

磁盘：随包模型约 430 MB（运行时真正读取的 int8 流式权重 ~199 MB，加上 242 MB 的 IPA q4 模型）。run 目录通过**硬链接**预置工作区副本，同卷下不产生额外磁盘占用。

## 容量速查

| 服务器 | 在线 | 同时说话（流式引擎） |
|---|---|---|
| 4 核 / 8 GB | ~10–20 | 3–6 |
| 16 核 / 16 GB | ~50 | 8–12 |
| 32 核 / 32 GB | ~100 | 15–25 |

**当前版本 ≤20 人开箱即用。** 当前的硬约束是**每会话整份模型加载**（每人 ~250–400 MB 原生内存，在 JVM 堆之外）。100 人级服务器需要先实现：

1. 实现设计 §3.3 的**每引擎共享 `OnlineRecognizer`**（共享识别器 + 每会话独享 `OnlineStream`）——把会话层压缩到仅剩流状态；
2. 识别器闲置 30–60 秒后关闭、按需重建；
3. IPA 解码池大小可配置 / 过载降级。

## 降负载的配置手段（现在就能用）

- `[server] maxFramesPerSecond`：调低可限制滥用客户端的吞吐（语音质量略降）；
- `[engines] allowed`：当前每个放行的流式引擎都要**每说话会话**加载一份完整模型——收紧 `allowed`（例如移除最贵的 `ipa-phonemes` 推理路径）是最强手段。流式模型本身一套权重就覆盖 zh+en，不存在按语言省内存的空间；
- `[server] enabled = false`：彻底关闭（空载）。

## 监控与诊断

- 共享层首次使用时打一条日志：`Server voice engine ready: <engine>` / `Shared IPA engine ready`；
- 每会话引擎按玩家打日志：`sherpa streaming recognizer ready (engine=…, hotwords=…)`——每个说话玩家一条，每条对应一次模型加载；
- `-Dvoicecast.verbose=true` 输出每帧/每句的管线日志（排障用，生产建议关闭）；
- 会话队列有界（32 帧，满时**丢弃新到帧**（drop-new），保留旧帧时序），过载时表现为"句子偶尔不识别"而非卡顿崩溃。
